### 1b. The FX-cue consumer (DORMANT behind `solreign.fx.cue_v1`, default false)

`SolreignChangelingSystem.ArmBlade.cs`'s `ExtendArmBlade`/`RetractArmBlade` each now also call a
new private helper, `RaiseArmBladeTransformationCue`, which calls the existing (W2-shipped,
already-reviewed) `ISolreignFxCueRaiser.RaiseSecretRoleCue` with `EffectId: "transformation"` —
the language's first real consumer. `RaiseSecretRoleCue` is entirely gated inside itself behind
`solreign.fx.cue_v1` (checked first thing, returns `false` if disabled) — this call site adds no
gate of its own, matching the spec's "the raise helper is where the gate lives" idiom.

Extend uses distinct, non-default parameters (intensity 0.85, scale 1.1, duration 1.2s, palette
1, phase 0) from Retract (intensity 0.5, scale 0.9, duration 0.6s, palette 2, phase 1) — a
deliberate design choice (Extend = the dramatic reveal beat, Retract = the lesser undo beat), both
well within `effects.yml`'s existing `transformation` prototype bounds. A missing player session
(admin-spawned/NPC changeling) is a safe no-op — the cue is decorative, never gameplay-critical
(spec §4.0), so skipping it changes nothing about the already-applied damage/appearance change.

## 2. The confidentiality mechanism used

`transformation` is `DetailOnly` + `requiresRedactedBroadcastVariant: true` in the existing
`effects.yml` (W3-shipped, unchanged this session), with `genericVariant: transformation_generic`.
Per spec §5.2 (W2-shipped, unchanged this session), `RaiseSecretRoleCue` is the **only** legal
raise path for a `DetailOnly` id — `RaiseCue` hard-refuses it. Calling `RaiseSecretRoleCue` always
emits, in one call:

1. A **detail cue** — the real `EffectId`, the real (non-default) intensity/scale/duration/
   palette/phase this worktree passes, session-targeted (`RaiseNetworkEvent(detailCue, actorSession)`)
   to the changeling's own connection only.
2. A **generic cue** — `EffectId: transformation_generic`, every numeric field scrubbed to that
   prototype's own fixed defaults (never the detail cue's real values), an independently-rolled
   seed, broadcast via `Filter.Pvs(pvsSource).RemovePlayer(actorSession)` (PVS-scoped, actor
   excluded so there's no double-render).

This worktree's own contribution to confidentiality is entirely the **call site** — using real,
distinct, non-default parameters for the detail cue while relying on the pre-reviewed raiser for
the scrub/split/actor-exclusion machinery itself. No new confidentiality primitive was built here;
W2 already built and reviewed it. What this worktree adds is the first real proof that a real
gameplay caller uses it correctly.

**Confidentiality property, stated precisely:** a bystander within PVS range of an
Extend/Retract can tell "some transformation happened on that body" (a `transformation_generic`
cue, same id every non-secret-role transformation moment would eventually also use per spec
§2.2's `body_shock_generic`/wave-2-producers plan) but never that it was specifically the
`transformation` id, never the real intensity/palette/phase, never a shared seed with the actor's
own detail cue. The visible arm-blade sprite itself is **not** part of this confidentiality
boundary — spec §5.2/§6.2 states appearance data is public gameplay state by design (the blade
being visible is the point; only the pre-reveal metadata is protected), and §1a's fix is exactly
that public channel.

## 3. A real grounding correction mid-session (read before trusting §1a blindly)

The spec's literal §6.2 sample YAML (`GenericVisualizer` on `MobLing`) does not work as written,
for two compounding reasons discovered and fixed this session:

1. **`MobLing` is a preview/admin-spawn dummy, not what a real changeling actually is.** Grepping
   confirmed real in-round changelings are granted their components via
   `Resources/Prototypes/Roles/Antags/changeling.yml`'s `antagSpecifier` (applied by
   `AntagSelectionSystem.AssignAntagComponents` onto whatever body — Human, Moth, whatever species
   — the player already had), never by spawning a separate "changeling species" entity. The
   existing `SolreignChangelingTransformCycleIntegrationTest.cs` already modeled this correctly
   (`SpawnEntity("MobHuman", ...)` + `EnsureComponent<SolreignChangelingComponent>`), which is what
   first raised the question of whether `MobLing`-only wiring would ever reach a real player.
2. **`GenericVisualizerComponent` cannot be granted this way at all**, confirmed via grk
   adversarial review + direct engine-source verification: it is a `Robust.Client`-only,
   non-`[NetworkedComponent]` type. The server's `IComponentFactory` resolves the name
   `"GenericVisualizer"` as `ComponentAvailability.Unknown` (it isn't in
   `Content.Server/Entry/IgnoredComponents.cs`'s explicit ignore list, and the one broader ignore
   rule there only matches names ending in `"Visuals"`), so `ComponentRegistrySerializer` drops it
   at YAML-parse time — `AntagSpecifierPrototype.Components` never even contains the entry, and
   `AssignAntagComponents`'s `EntityManager.AddComponents` loop never sees it. Even in principle,
   there is no wire path for a non-networked, client-only component type to reach a client via a
   server-side component grant. Contrast with `Resources/Prototypes/Entities/foldable.yml`'s
   `BaseFoldable` (a real, shipped, working `GenericVisualizer` usage): that works because it's an
   **entity prototype**, independently parsed by each side's own `IPrototypeManager` — the client
   builds its own real `GenericVisualizerComponent` instance straight from its own copy of the
   shared YAML at spawn time, entirely independent of what the server did with its copy. A role
   grant has no such independent-construction path.

**A first attempt this session used exactly the spec's literal sample** (`GenericVisualizer` added
to both the `antagSpecifier` and `MobLing`). It built, and a test spawning `MobLing` directly
passed — but that test alone couldn't distinguish "the fix works" from "`MobLing`'s own prototype
happens to load `GenericVisualizer` client-side regardless of the antagSpecifier grant." A grk
adversarial review pass (see §4) caught the antagSpecifier half was dead code before this was
shipped as correct. The fix: removed `GenericVisualizer` from both YAML files entirely, replaced
with §1a's `SolreignChangelingArmBladeVisualsSystem`, and added a new regression test
(`ExtendArmBlade_OnARealAntagGrantedMobHumanBody_TogglesArmBladeLayerToo`) that calls the exact
same `AntagSelectionSystem.AssignAntagComponents(uid, "Changeling")` a real round rule calls, onto
a plain `MobHuman` — mutation-checked (disabling the new system's subscription made this test AND
the `MobLing` test fail; re-enabling made both pass again).

**Lesson banked for future worktrees:** a test spawning the "obviously correct" preview/dummy
entity for a feature is not sufficient proof the feature reaches a *real* instance of that
gameplay role if the role is granted onto an arbitrary pre-existing body rather than spawned from
a dedicated prototype.
