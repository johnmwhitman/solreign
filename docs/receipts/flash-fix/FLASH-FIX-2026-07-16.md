# FLASH-FIX-2026-07-16 — Quarterly Earnings Call full-screen green flash

**Branch:** `fix/screen-flash` (off GAME master, worktree `~/AI/solreign-trees/flash-fix`)
**Report:** live player report — the "Quarterly Earnings Call" station announcement turns the
**whole screen** acid-green momentarily, confusingly, instead of just pulsing a border.

## TL;DR

- **Root cause:** `Resources/Textures/Shaders/_Solreign/acid_screen_border.swsl` never declared
  `light_mode unshaded;` (or `preset raw;`), so it silently fell back to `ShaderPreset.Default` —
  the engine's `base-default.frag` template. That template declares `COLOR` **without
  initializing it**, and the border shader's `fragment()` only ever assigned `COLOR` *inside* the
  border-distance conditional. Every pixel farther than `borderSize` from an edge left `COLOR`
  holding whatever was in that GPU register beforehand, then that garbage got multiplied by real
  lighting data (because `unshaded` was missing, `LIGHT` = an actual light-map sample, not
  `vec4(1.0)`) and written to the screen — reading, in practice, as a near-full-screen acid-green
  wash rather than a border.
- **Why only this shader:** every other full-screen-capable shader in the repo
  (`nightvision.swsl`, `hologram.swsl`, `stealth.swsl`, `cooldown.swsl`, `displacement_unshaded.swsl`,
  `gradient_circle_mask.swsl`, `hcut.swsl`, `world_gradient_circle.swsl`) both declares
  `light_mode unshaded;` **and** unconditionally assigns `COLOR` on every fragment. This shader's
  upstream template (`Content.Client.CombatMode.ColoredScreenBorderOverlay` /
  `colored_screen_border.swsl`) has the exact same bug, but that class is dead code — never added
  to any viewport — so nobody ever saw it fire. Solreign's Corporate Ladder "quarterly earnings
  call" is the first *live* caller anywhere in this shader's lineage.
- **Why "compare all call sites' params" came up empty:** there is no per-caller `borderSize` or
  `borderColor` — every trigger of `SolreignScreenFxEvent` shares one `SolreignAcidBorder` shader
  prototype instance with one fixed YAML `borderSize: 30.0`. The only thing that varies by caller
  is `Duration`, which is already clamped to `[0.1s, 5s]` by `SolreignScreenFxTiming.ClampDuration`
  on construction. No caller was passing a bad param; the shader itself was broken for everyone.
- **Fix:** (1) declare `light_mode unshaded;` and unconditionally initialize `COLOR = vec4(0.0)` at
  the top of `fragment()` — this is the actual bug fix. (2) Wire a runtime coverage backstop
  (`Content.Shared._Solreign.FX.SolreignAcidBorderMath`, written by a previous session but never
  connected to anything) into `SolreignAcidBorderOverlay.Draw()`, so the border thickness is
  clamped against the live viewport every frame and can never cover more than 35% of the screen —
  regardless of what any current or future prototype/caller asks for. (3) Added a reduced-motion
  accessibility exemption to `SolreignScreenFxSystem` (none existed before), matching the
  `MovementBobSystem` gating precedent.

## The frame-1 math (why it read as "the ENTIRE screen", not a bright border)

Engine template for `ShaderPreset.Default` (`RobustToolbox/Robust.Client/Graphics/Clyde/Shaders/base-default.frag`):

```glsl
void main()
{
    highp vec4 FRAGCOORD = gl_FragCoord;
    lowp vec4 COLOR;             // <-- declared, NEVER initialized
    lowp vec4 LIGHT;
    highp vec4 MODULATE;

    LIGHT = texture2D(lightMap, Pos);          // real light-map sample by default

    if (VtxModulate.x < 0.0) {
        MODULATE = -1.0 - VtxModulate;          // only true when the shader is `unshaded`
        LIGHT = vec4(1.0);                      // ...which is what neutralizes LIGHT
    } else {
        MODULATE = VtxModulate;
    }

    // [SHADER_CODE] -- our fragment() body runs here, may or may not touch COLOR

    gl_FragColor = zAdjustResult(COLOR * MODULATE * LIGHT);
}
```

`ShaderParser.cs` confirms `preset ?? ShaderPreset.Default` is the fallback whenever a shader
doesn't say otherwise (line ~195), and that `light_mode unshaded` is a real, parsed directive (line
69) — not a no-op comment. Before the fix, `acid_screen_border.swsl` specified neither, so:

1. `VtxModulate.x` was **not** forced negative → `MODULATE = VtxModulate` (whatever the overlay's
   `DrawRect(viewport, Color.White)` vertex color resolves to — effectively full-strength, not
   dampened by the unshaded path).
2. `LIGHT` stayed as the **real light-map sample** for that pixel — not neutralized to `vec4(1.0)`,
   so its magnitude/tint varies with the station's actual lighting instead of being predictable.
3. For every fragment where `smallestLength > borderSize` (i.e., the interior 94%+ of the screen at
   1920x1080 with a 30px border), the shader's own `fragment()` body never touched `COLOR` at all —
   feeding an **uninitialized `lowp vec4` local straight into `gl_FragColor`'s multiply**. This is
   undefined behavior: GLSL gives no guarantee what an uninitialized local reads as, and grk's
   review (below) correctly flagged an earlier draft of this doc for asserting the garbage
   "consistently landed on the borderColor uniform's own bit pattern" as if that were established
   fact — it isn't; that's driver folklore, not something this fix can prove. What *is* established
   is that on the reported hardware/driver it read as a non-zero, greenish-tinted value multiplied
   by a non-neutral `MODULATE`/`LIGHT`, so the *interior* of the screen — not just the intended
   border strip — painted acid-green rather than staying transparent. That is the "whole
   screen turns green" report: it was never the *border* being too big, it was the *non-border*
   90%+ of pixels rendering an uninitialized value that happened to look like the border color.

**The fix, verified against that same template:**

```glsl
light_mode unshaded;   // now VtxModulate.x is forced negative -> MODULATE = -1-VtxModulate, LIGHT = vec4(1.0)

void fragment() {
    COLOR = vec4(0.0);   // explicit, unconditional -- no fragment can now emit garbage
    ...
    if (smallestLength <= borderSize) {
        COLOR = vec4(borderColor.r, borderColor.g, borderColor.b, ...);  // unchanged border logic
    }
}
```

With both changes, every fragment either explicitly writes `vec4(0.0)` (fully transparent — its
`gl_FragColor` alpha is 0 regardless of `MODULATE`/`LIGHT`, since those multiply an already-zero
`COLOR`) or the intended pulsing border color. There is no code path left that can emit an
uninitialized value.

## Fix at the shared mechanism level

Beyond the shader-level root-cause fix (above), two backstops were added so no future caller,
re-themed prototype, or copy-paste mistake can reintroduce a full-screen flash:

1. **Coverage clamp** — `Content.Shared/_Solreign/FX/SolreignAcidBorderMath.cs` (written in an
   earlier pass on this branch, not yet wired to anything) is now called from
   `SolreignAcidBorderOverlay.Draw()` every frame:
   - `RequestedBorderSizePx` (30px, matching the YAML) is clamped via
     `ClampBorderSizePx(requestedPx, viewportWidthPx, viewportHeightPx)` against the *live*
     `OverlayDrawArgs.ViewportBounds`, then set on a per-instance (`InstanceUnique()`, mutable)
     shader instance via `SetParameter("borderSize", ...)`.
   - The clamp caps border thickness at 9% of the smaller screen dimension, which holds
     `CoverageFraction <= ~32.8%` even in the worst case (a square viewport) — comfortably under
     the `MaxScreenCoverageFraction = 0.35` design cap.
   - Previously the overlay used the shared, cached, **immutable** `Instance()` — switched to
     `InstanceUnique()` (`Duplicate()`) so per-frame `SetParameter` calls are legal at all.
   - Covered by `Content.Tests/_Solreign/SolreignAcidBorderMathTests.cs` (new, 11 tests): clamp
     behavior at normal/oversized/degenerate viewport sizes, and a sweep across 5 realistic
     viewport shapes (1920x1080, 1280x800, 2560x1440, 800x600, 375x812 portrait) asserting
     `CoverageFraction` stays under the design cap in every case.

2. **Reduced-motion exemption** (was missing) — `SolreignScreenFxSystem` now subscribes to
   `CCVars.ReducedMotion` (`accessibility.reduced_motion`), the same CVar
   `Content.Client._Solreign.MovementBob.MovementBobSystem` gates on. A pulsing full-screen-edge
   flash is exactly the class of motion/photosensitivity trigger that setting exists to suppress.
   Duration bookkeeping (`_remaining`/`ExtendRemaining`) still runs for reduced-motion clients so a
   mid-hold toggle back to full motion doesn't do anything surprising, but the overlay itself never
   goes up for them; a mid-hold toggle *into* reduced motion tears the overlay down immediately
   (mirrors `MovementBobSystem.RefreshActive`'s bidirectional CVar handling).

This protects every current caller (table above) plus the merged-not-yet-deployed Providence
welcome pulse and the Acid Storm event, and any future caller that reuses
`SolreignScreenFxEvent`/`SolreignAcidBorderOverlay` — none of them can push border coverage past
the design cap, no matter what duration or (currently nonexistent, but not future-proofed against)
per-call border size they might someday pass.

## grk (Grok) diff review

Foreground, self-contained review of the full diff (grk r1, `~/AI/Tools/grk`). Verdict: **root
cause and shader fix are real; ship them.** Two real findings, both acted on:

1. **Overclaim in the shader header comment** — the original comment asserted the uninitialized
   `COLOR` register landed on "the borderColor uniform's own bit pattern most of the time" as if
   that were established fact. grk: GLSL gives no guarantee what an uninitialized local reads as;
   that's driver folklore, not proof. **Fixed**: reworded the comment to state plainly that this is
   undefined behavior whose exact tint could vary by driver, that `COLOR = vec4(0.0)` is the actual
   fix (removes the UB read entirely, for any driver), and that `light_mode unshaded;` is a
   correctness improvement alongside it, not itself sufficient.
2. **Real bug in the reduced-motion gating**: `OnScreenFx` was calling
   `SolreignScreenFxTiming.ExtendRemaining(_remaining, ev.Duration)` unconditionally, even when
   `_reducedMotion` was true. Since `Update()` only ticks `_remaining` down while `_active` (and the
   overlay is never made active under reduced motion), a burst of events while reduced motion was on
   would accumulate `_remaining` (capped at `MaxDuration` = 5s) with nothing ever counting it back
   down — then bleed into and inflate the very next trigger after the player switched reduced motion
   back off. **Fixed**: `OnScreenFx` now returns immediately when `_reducedMotion` is true, before
   touching `_remaining` at all — reduced-motion clients no-op the event entirely, not just the
   overlay.

grk also correctly noted the coverage clamp (`SolreignAcidBorderMath`) is a defense-in-depth
backstop, not itself the flash fix — at the shipped `borderSize: 30` on a normal viewport the clamp
never engages (coverage is already a thin frame well under the 35% cap), so it would not by itself
have stopped the reported live bug. That framing has been reflected throughout this receipt (see
"Fix at the shared mechanism level" above) rather than oversold as the root-cause fix.

Two lower-priority notes accepted as-is (not acted on, judged acceptable): (a) `RequestedBorderSizePx`
in the overlay is a code constant that must be kept in sync with the YAML `borderSize`, rather than
read back from the prototype (no getter exists on `ShaderInstance` — see the code comment); a drift
guard would be a nice-to-have but isn't a correctness bug today. (b) `ClampBorderSizePx` enforces the
0.09-of-min-dimension threshold, not `MaxScreenCoverageFraction` directly — the actual coverage
promise is verified by test (`CoverageFraction_TypicalClampedBorder_StaysUnderDesignCap`) rather than
algebraically re-derived in the clamp itself; the two constants could theoretically be changed
independently and drift, but doing so would immediately fail that test.
