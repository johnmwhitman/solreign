## 2. H1 and M5 closure (the mission's two named inherited obligations)

### H1 — DetailOnly audience classification never checked in `TryValidateReceived`

W1's receipt dispositioned this as "not fixable at this layer, by design... tracked as W2's
obligation." Closed in two halves:

1. **Send side** (`SolreignFxServerSystem.RaiseCue`): hard-refuses any EffectId whose allowlist
   classification is `DetailOnly` — `DebugTools.Assert` in Debug builds, drop+metric in Release.
   Only `RaiseSecretRoleCue` may put a `DetailOnly` id on the wire, and it always emits the
   generic+detail pair itself. This is the API-enforced split spec §5.2 requires.
2. **Receive side** (`SolreignFxReceiveGuard.CheckDetailOnlyAnchor`, pure logic): a receiving
   client genuinely cannot tell from the payload whether it was PVS-broadcast to it or
   session-targeted — W1's own honest finding. The defense-in-depth check instead verifies a
   structural invariant: v1's only `DetailOnly` primitive (`transformation`) is, by spec's own
   design, always entity-anchored to the secret-role actor's own body and always delivered
   session-targeted to that actor. Any received `DetailOnly` cue that is coordinate-anchored,
   unanchored, or entity-anchored to anything other than this client's own
   `IPlayerManager.LocalEntity` is rejected and logged as a confidentiality anomaly, never
   rendered — regardless of what `TryValidateReceived` already accepted as structurally
   well-formed. Wired into `SolreignFxCueSystem.OnCueReceived` immediately after
   `TryValidateReceived` succeeds.

Mutation-checked: disabled the anchor-mismatch branch, confirmed 2 tests
(`CheckDetailOnlyAnchor_DetailOnly_AnchoredToADifferentEntity_IsRejected`,
`..._NoLocalControlledEntity_IsRejected`) failed, reverted.

### M5 — Palette/phase fallback under a `count <= 0` prototype can mint a meaningless index

W1's receipt dispositioned this as "the correct fix is keeping a malformed prototype out of the
allowlist at load time, which is W2/W3's job to wire." Closed via `SolreignFxPrototypeSource.cs`:
wraps a raw prototype loader (`ISolreignFxRawPrototypeLoader`, backed by
`IPrototypeManager.TryIndex` on each side) with `SolreignFxCuePrototypeValidation.Validate` — a
prototype failing ANY W1 §1.5 rule (including `PaletteCount <= 0`) is cached as INVALID and
`TryResolve` returns `false` for it, exactly as if the id didn't exist. `TryCreate`/
`TryValidateReceived` therefore reject at the earlier "EffectIdNotResolved"/"EffectIdRejected"
step and never reach the palette/phase fallback with a malformed count. Validation results are
cached per id, invalidated on `IPrototypeManager.PrototypesReloaded`.

Both client and server construct their own `SolreignFxPrototypeSource` instance wrapping their
own `IPrototypeManager` — same "each side supplies a real implementation" pattern W1 already
established for `ISolreignFxCuePrototypeSource`/`ISolreignFxAnchorResolver`.

| H-B | Same pattern in `RaiseSecretRoleCue`: detail budget consumed → generic budget fails → returns false with no refund, detail key still coalesced → later same-tick call returns true while neither half was raised | **Fixed.** Both cues now constructed first; a new `SolreignFxEgressBudget.TryConsumePair` peeks BOTH categories' bucket availability (via a non-mutating `Available()` check) and the combined 2-unit global-tick cost BEFORE committing either — a failure on either side leaves neither bucket touched and neither key marked coalesced |

## 5. Justified deviations from a literal reading of the spec

1. **New `Content.Shared` files beyond W1's set** (`SolreignFxAnchorKey.cs`, `SolreignFxCategory.cs`,
   `SolreignFxProfilePolicy.cs`, `SolreignFxDropAggregator.cs`, `SolreignFxPrototypeSource.cs`):
   spec's W2 file boundary names only `Content.Client`/`Content.Server` files, but several pieces
   of logic are genuinely needed by BOTH sides (anchor-key equality for merge/coalesce, category
   budget defaults, drop-diagnostics rate-limiting, validated prototype resolution for M5). Same
   engine-decoupled-shared-logic rationale W1 already used for `ISolreignFxCuePrototypeSource`/
   `ISolreignFxAnchorResolver`.
2. **`SolreignFxProfileGateSystem.cs`** (not `SolreignFxProfileGate.cs`) is the name used for the
   `Content.Client` wrapper — kept distinct from W1's `Content.Shared._Solreign.FX.SolreignFxProfileGate`
   (different namespace, same base name) rather than colliding with it. W1's own receipt already
   flagged this exact naming tension and explained why the pure math had to live in Shared for W1;
   this session's `...System` suffix follows the same `MovementBobMath`/`MovementBobSystem` split
   the codebase already uses elsewhere.
3. **`SolreignFxCuePrototype.cs` extended with three new fields** (`DefaultIntensity`/
   `DefaultScale`/`DefaultDuration`) even though that file is W1's. Necessary: `RaiseSecretRoleCue`
   cannot implement spec §5.2's "scrub to the generic prototype's fixed default values" without
   some field to scrub to, and none existed. Load-time validated in the same
   `SolreignFxCuePrototypeValidation.Validate` pass W1 already established, same
   never-let-the-fallback-itself-be-invalid rationale as the existing palette/phase defaults.
4. **One global pool-cap-scale CVar rather than ~9 categories × several per-category CVars**:
   spec §3 says "each is a CVar default" for the budget table; W2 ships `solreign.fx.pool_cap_scale`
   (a single admin dial) plus the CVars that gate rate/behavior (egress tick cap, refill
   multiplier, client intake) instead of a full per-category CVar matrix, given the budgets are
   already spec's own "provisional engineering defaults" pending the Lab profiler's revalidation
   pass (§3's own stated caveat) — revisit if that pass calls for finer per-primitive tuning.
5. **`SolreignFxDiagnosticsSystem.cs`** exists in W2's Content.Server boundary even though spec §8's
   literal W2 file list doesn't name it — it's the "new, tiny `SolreignFxDiagnosticsSystem`" spec
   §1.3a.5 itself names as the real `ISolreignFxCorrelationSource` implementation; there is no way
   to implement `RaiseCue`/`RaiseSecretRoleCue` without it.

No other deviations. Every other file, method, and test maps directly onto an explicit line item
in the spec, the mission's restatement of it, or a grk-review finding.
