# HTN pool-race flake — root cause + fix — 2026-07-16 (HANDOFF §10 v2)

Branch: `fix/htn-pool-race` (worktree `~/AI/solreign-trees/flake-htn`, GAME repo `~/AI/Kolton-SS14/server`)

## Symptom

`NullReferenceException` at `NPCBlackboard.TryGetEntityDefault` (`Content.Server/NPC/NPCBlackboard.cs:154`,
`var handSys = entManager.System<HandsSystem>();`), reached via a precondition's
`IsMet` (e.g. `CoordinatesNotInRangePrecondition`), reached from `HTNPlanJob.Process`
running on the CPU job queue. Flaky only inside the full integration-test battery
(`SolreignTameableSystemIntegrationTest`'s `Feed_AlreadyTamed_*` and other tests were
historically hit, "AllAtOnce"-era cases per earlier notes), never when run solo, and
always landed on whichever test happened to run next ("rotating victim").

## Inventory at relaunch

The worktree already had two uncommitted, non-crashing, correctly-diagnosed-in-spirit
changes from a prior killed session:

- `Content.Server/NPC/HTN/HTNPlanJob.cs`: extra `Cancellation.IsCancellationRequested`
  checks at the top of the planning loop and right after `await primitive.Operator.Plan(...)`.
- `Content.Server/NPC/NPCBlackboard.cs`: made `HandsSystem` resolution in
  `TryGetEntityDefault` lazy (only in the `switch` cases that need it) instead of eager
  for every key lookup — this is why the crash "rotated" across unrelated preconditions
  (any key lookup paid for the same shared, eagerly-resolved call).

Both were kept (the `NPCBlackboard.cs` change is net-positive and still valid; the
`HTNPlanJob.cs` checks are defense-in-depth, see below). Neither, alone, closed the
actual gap — no test, no receipt, nothing committed.

## Root-cause investigation (this session)

The prior session's own code comments asserted operator continuations (e.g.
`MoveToOperator` awaiting `PathfindingSystem.GetPath`) "resume on whatever thread
completed that work." **This is false and was corrected.** Traced the actual
mechanism through the engine:

- `RobustToolbox/Robust.Shared/Asynchronous/TaskManager.cs` installs a custom
  `RobustSynchronizationContext` on the server's own thread at startup. Every await in
  this code path funnels its continuation through that context's channel, drained by
  `TaskManager.ProcessPendingTasks()` (`RobustToolbox/Robust.Server/BaseServer.cs:753`),
  called at a fixed point every tick, before `_entityManager.TickUpdate(...)`. Operator
  continuations always land back on the server's own instance thread — never a raw
  ThreadPool thread. `PathfindingSystem.GetPath`'s `Parallel.For` search runs on worker
  threads, but the completion signal (`path.Tcs.SetResult`,
  `Content.Server/NPC/Pathfinding/PathfindingSystem.cs:165`) only fires from the
  single-threaded tick cleanup. `Robust.Shared/CPUJob/JobQueues/Queues/JobQueue.cs` is
  explicitly single-threaded ("At one point I tried making the pathfinding queue
  multi-threaded but ehhh didn't go great").
- The **real** gap is queue *lifetime*, not threading. `HTNSystem` (`Content.Server/NPC/HTN/HTNSystem.cs`)
  keeps one long-lived `JobQueue _planQueue` for the life of the server/EntityManager.
  An `HTNPlanJob` (`Content.Server/NPC/HTN/HTNPlanJob.cs`) that's still `Waiting`/`Pending`
  inside that queue is not removed by cancelling `HTNComponent.PlanningToken` —
  `CancellationTokenSource.Cancel()` only flips a flag; `Job<T>.Run()`
  (`RobustToolbox/Robust.Shared/CPUJob/JobQueues/Job.cs:130`) only *observes* that flag
  the next time the queue happens to call `Run()` on it. Nothing dequeues the job
  itself, and nothing waits for it to finish.
- `Content.IntegrationTests/Pair/TestPair.Recycle.cs:35-59` (content-side, not engine)
  is how a server gets handed back to the pool between tests: it calls
  `gameTicker.RestartRound()` (twice) and pumps exactly one tick (`RunTicksSync(1)`)
  each time. It never checks `HTNSystem`'s internal `_planQueue` state. `RestartRound()`
  → `ResettingCleanup()` (`Content.Server/GameTicking/GameTicker.RoundFlow.cs:704-719`)
  raises `RoundRestartCleanupEvent` then calls `EntityManager.FlushEntities()` — which
  *does* delete every entity (and does fire `ComponentShutdown`/`OnHTNShutdown` per HTN
  NPC) — but a plan job that's genuinely still `Waiting` (e.g. on an in-progress
  pathfind) at that instant keeps sitting in the queue regardless, because cancelling
  its token doesn't dequeue it.
- `Content.IntegrationTests/Tests/_Solreign/SolreignZoneGateIntegrationTest.cs:31-39`
  independently confirms this: it sets `PoolSettings.Fresh = true` specifically because
  "the stale-EntityManager HTN NPC race (HANDOFF §10) repeatedly picks this test as its
  victim in full-battery runs" — a workaround for the same leak, not a fix.

So: a leaked `HTNPlanJob` can survive a round restart (or, in integration tests, a pool
recycle) and resume on a *later* tick — on the same instance thread, same recycled
`EntityManager`/`HTNSystem` — belonging to whatever test/round now owns that server,
dereferencing blackboard/entity state that isn't its own. Cancellation-token checks
alone have a residual timing window (token cancelled on tick N, job not re-`Run()`
until tick N+k) that can't be closed by adding more checks inside the job.

## Fix (content-side only; RobustToolbox untouched)

`Content.Server/NPC/HTN/HTNSystem.cs`:

- `_planQueue` is no longer `readonly`.
- New `DiscardPlanQueue()`: cancels every `HTNComponent.PlanningToken` (belt and braces,
  unchanged from the prior partial fix) **and replaces `_planQueue` with a brand-new,
  empty `JobQueue`**. Whatever was enqueued — finished or not — becomes permanently
  unreachable: nothing can ever call `Run()` on it again, independent of tick timing.
- Called from `Shutdown()` (was already partially doing the cancel-loop) and from a new
  `SubscribeLocalEvent<RoundRestartCleanupEvent>(OnRoundRestartCleanup)` — the actual
  per-round/per-pool-recycle boundary, firing synchronously inside the same event
  dispatch `RestartRound()` raises, before `EntityManager.FlushEntities()` even runs.

`Content.Server/NPC/HTN/HTNPlanJob.cs`: kept the prior session's two
`Cancellation.IsCancellationRequested` checks (top of planning loop; after
`Operator.Plan` await) as defense-in-depth, but corrected the comments — removed the
incorrect "resumes on a different thread" claim and replaced with the verified
queue-lifetime mechanism.

`Content.Server/NPC/NPCBlackboard.cs`: kept the prior session's lazy `HandsSystem`
resolution in `TryGetEntityDefault` — still a valid, orthogonal improvement (an
unrelated key lookup no longer pays for/can't fail on a `HandsSystem` resolution it
never needed).

`SolreignZoneGateIntegrationTest.cs`'s `PoolSettings.Fresh = true` workaround was left
in place (cheap insurance, not test-weakening) — it's now redundant for the HTN
mechanism specifically, but harmless.
