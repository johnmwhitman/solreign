## 3. Root cause

Cross-feature interaction between the pool's initial spawn, wow-wiring's delayed beat, and this
test's documented manual clock jump:

1. The pool pair (`Connected = true, DummyTicker = false`) performs a REAL player spawn during pair
   setup, before the test body. With wow-wiring's CVars at default (on) and a fresh solo-run ledger
   (`career.Tours == 0`), `ProvidenceWelcomeSystem.OnPlayerSpawnComplete` →
   `LoadWelcome` → `ScheduleFirstShiftPersonal` (ProvidenceWelcomeSystem.cs:239) enqueues a
   personal-welcome beat due at `CurTime + 8s`.
2. The ConsentFlow test body jumps `IGameTiming.CurTick` forward ~5 minutes
   (WingmateSystemIntegrationTest.cs, decline-cooldown step) — intentionally, documented, and safe
   for the Wingmate system itself. The jump trivially satisfies the pending beat's due-time.
3. Nothing ticks inside `WaitAssertion`, so the beat fires on the FIRST real tick rolled forward —
   which is `GameTest.DoTeardown`'s `Pair.RunUntilSynced()`. `ProvidenceWelcomeSystem.Update`
   (line 165) drains it → `FireFirstShiftPersonal` (line 281) → `PlayLineTo` → server audio
   creates a new audio entity.
4. `PvsSystem` realigns its per-tick dirty-buffer index (`_currentIndex`) in `CleanupDirty` at the
   END of each tick, as `(CurTick + 1) % DirtyBufferSize`. On the first tick after a manual
   +9001-tick jump, `_currentIndex` still reflects the pre-jump tick, so the first
   `OnEntityAdd` (PvsSystem.Dirty.cs:45) trips
   `DebugTools.Assert(_currentIndex == CurTick % DirtyBufferSize)` → server thread throws →
   `RunUntilSynced` rethrows in teardown → dirty dispose → test failed.

Not an engine bug and not a production bug: entity creation inside `Update` is normal; the assert
only trips because the test mutated `CurTick` out-of-band (a technique the test already documents
as pool-safe via `Dirty = true`). Not a Wingmate bug either — the pending beat is pool-setup
contamination from an unrelated system. wow-wiring's own tests anticipate exactly this and clear it
via `ProvidenceWelcomeSystem.ResetRoundStateForTests()` (see that method's doc comment: "a
pool-connected session already goes through a REAL spawn during pool setup … which already
schedules a real pending personal beat the test never asked for").

Why the wow-wiring branch battery (175/0/1) didn't catch it: in a full battery the shared
per-instance season ledger and pair recycling make `career.Tours == 0` / beat-still-pending at
ConsentFlow's clock jump non-guaranteed; a fresh SOLO pair hits it deterministically.
