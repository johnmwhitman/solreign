## 2. The W2 file edit — exact diff shape

Spec §8's W3 file boundary lists no `Content.Client/_Solreign/FX/SolreignFxCueSystem.cs` edit, but
building a real renderer requires hooking the exact points where W2's lease lifecycle already lives
(lease granted, lease released, pool rebuilt, system shutdown) — there is no way to add rendering
without SOME hook into that lifecycle. Rather than duplicate W2's lease-tracking logic in a second
system (which would double-process every cue and risk desyncing from the authoritative `_active`
list), this session added six small, additive `partial void` hook declarations/call-sites to the
existing file:

1. `OnPoolRebuilt(capacities)` — called at the end of `RebuildPool()`.
2. `OnLeaseAcquiredForRender(cue, category, lease)` — called right after `UpsertActiveEffect` in
   `OnCueReceived`.
3. `OnTransformationCue(cue)` — replaces a bare `return` in the pre-existing Transformation
   early-return branch (that branch never touched the pool; it needed a distinct one-shot hook).
4. `OnLeaseReleasedForRender(lease)` — called at both `FrameUpdate` release paths (anchor died /
   natural expiry) and the kill-switch mass-release loop in `OnProfileChanged`.
5. `OnFrameTick(frameTime)` — called once per `FrameUpdate`.
6. `OnSystemShutdown()` — called from `Shutdown()`.

`partial void` methods with no implementation compile to a no-op — this file's behavior is
byte-identical to W2's shipped version when compiled WITHOUT `SolreignFxCueSystem.Rendering.cs`
in the assembly. A seventh change, NOT a hook: `RebuildPool()` now releases every currently-active
lease's render-side resources (`OnLeaseReleasedForRender`) BEFORE wiping `_active`, closing a leak
W2's own docstring flagged as future work ("simple and safe since W2 has no real renderer yet...
a future W3/W4 revisit can migrate active leases across a resize") — W3 is that revisit.

## 6. Justified deviations / honest scope trims

1. **`SolreignFxPooledSpriteComponent` moved from `Content.Client` to `Content.Shared` mid-session.**
   First drafted as a client-only marker (matching the mission's framing of "pooled cosmetic sprite"
   as a client concept) — but `Resources/Prototypes` is a SHARED tree the server also loads, and the
   server's `IPrototypeManager` failed to resolve the `SolreignFxCosmeticSprite` entity prototype's
   `SolreignFxPooledSprite` component reference (`[ERRO] serialization: Unknown component
   'SolreignFxPooledSprite' in prototype!`), caught by the FULL Solreign integration-test run (not
   the two targeted FX tests, which don't happen to load every prototype). Fixed by moving the
   (still-empty, zero-behavior) marker to `Content.Shared._Solreign.FX` so both sides register it.
2. **Smoke's per-frame alpha decay is driven by plain `SpriteComponent.SetColor`, not a live
   per-layer `smoke_fog.swsl` shader instance.** The shader FILE and its prototype entry both ship
   (spec's W3 file boundary explicitly names `smoke_fog.swsl` as required new content, and it is
   present, loadable, and shader-prototype-valid) — but wiring a live per-instance shader onto a
   sprite LAYER (as opposed to `SpriteComponent.PostShader`, used for the other overlays) needed
   additional, less-precedented `PrototypeLayerData`/`LayerSetData` plumbing this session judged not
   worth the added risk for a primitive with no consumer yet (dust/smoke are the two "may drop to
   zero at `cosmetic_minimal`" pure-cosmetic primitives — the lowest-stakes of the eight). The
   decay CURVE itself (`1 - progress²` ease-out) is identical math to the shipped shader; only the
   execution path differs. Flagged here rather than silently claimed as "shader-driven."
3. **Transformation's burst-sprite entities are NOT drawn from `SolreignFxRenderPool`** — spec §3's
   budget table gives Transformation an all-zero pooled-entity row ("rides GenericVisualizer, no
   extra entity"), so this session gives the cosmetic burst layer its OWN bounded mechanism: a true
   one-shot `Spawn` + `TimedDespawnComponent` (same idiom `MeleeWeaponSystem.Effects.cs` already uses
   for its own lunge-arc animation entities), self-cleaning after `Math.Clamp(cue.Duration, 0.1, 3)`
   seconds. This is NOT tracked by any concurrent cap of its own — bounded today only by (a) the
   server-side egress budget (W2, unchanged, already documented as accepting Transformation's
   "nominal egress-only burst of 8/tick" reasoning) and (b) the client's existing raw-receive flood
   cap (`SolreignFxCueSystem`'s `MaxRawReceivesPerFrameMultiplier`, checked upstream of ALL cues,
   including Transformation's). Worst case under a hostile server is a bounded, self-expiring spike
   (≤ ~128 transient entities/frame, each dying within ≤3s) — not unbounded, but also not capped by
   a NAMED Transformation-specific concurrent limit the way every other primitive is. Flagged as an
   open item for W4/W6 to revisit once a real consumer (and therefore a real load profile) exists,
   rather than inventing a speculative cap number now.
4. **`GenericVariant` assignment for `electrical`/`cast_ring`/`stamina_break`**: all three route to
   `body_shock_generic` (the only non-`transformation_generic` redacted id in v1's fixed 10-id
   vocabulary) — a content decision, not a spec-dictated one, closing W2's own grk finding M-G ("W3's
   effects.yml must configure a GenericVariant for every such primitive").
5. **Palette/phase counts and default colors per primitive are new creative content**, not derived
   from a spec-given table (spec deliberately leaves these to content authoring). Chosen for
   plausible variety (e.g. 4 spark tints for `impact_light/heavy`, 6 ability-school tints for
   `cast_ring`) without overengineering — easy to revise per art direction later; the load-time
   validation gate (§1.5) is what actually matters for correctness, not the specific counts.
