### 1a. `ArmBladeCycle_BystanderBroadcastStreamIsScrubbedAndGapFree_ActorGetsExactlyOneDetailPerEmit`

The full spec §5.3 scenario, superset of W4's deliberately-minimal preview
(`FxArmBladeConfidentialityIntegrationTest`, unchanged, still present and green). The scenario
interleaves three plain non-secret broadcast cues (`impact_light` via
`SolreignFxServerSystem.RaiseCue`, each raise's `bool` return asserted `true` so every emit is
server-side ground truth, not assumed) around BOTH halves of the arm-blade cycle (Extend AND
Retract — W4 only exercised Extend), each raise on its own tick so the egress budget's
within-tick coalescing never merges them. Then, per §5.3's numbered steps:

- **§5.3.3** — actor receives the real `transformation` detail cue for BOTH beats with the real
  non-default parameters (Extend 0.85/1.1/1.2s palette 1 phase 0; Retract 0.5/0.9/0.6s
  palette 2 phase 1).
- **§5.3.4** — bystander never receives the real id **on the raw wire**
  (`RawReceivedEffectIdsForTests`, recorded before any client-side gate — W4's own
  grk-mandated strengthening, reused); both generic cues are scrubbed to
  `transformation_generic`'s own fixed defaults (0.5/1.0/1.2s, neutral palette/phase). The
  **Retract** check is deliberately the sharper probe: the real detail duration (0.6s) DIFFERS
  from the generic default (1.2s), so a parameter leak is plainly visible — W4's Extend-only
  check could not distinguish scrubbed-vs-leaked duration because both were 1.2s. Seeds are
  independent per pair (Extend pair AND Retract pair).
- **§5.3.5 — the W5 headline** — the bystander's broadcast-stream CorrelationId sequence is
  asserted **pairwise strictly consecutive (+1 adjacency, not mere monotonicity)** across all
  five broadcast cues, even though two session-targeted detail cues were minted mid-scenario.
  Complemented from the actor's side: the two detail cues are consecutive in their OWN
  (targeted) namespace. Plus a cross-client consistency check: the actor and the bystander
  observed the SAME three non-secret broadcast cues (identical CorrelationIds) — the two
  clients' views differ ONLY at the secret-role pair boundary.
- **§5.3.5's actor half / §5.2 item 1** — actor never receives `transformation_generic` on the
  raw wire, for EITHER emit (W4 asserted this for one emit, at accepted level plus raw).
- **§5.3.6** — exactly one accepted detail activation per emit (`Has.Count.EqualTo(2)` across
  Extend+Retract): no double delivery, no dropped beat. (See §3.4 below for why "accepted cue"
  is the faithful proxy for "render activation.")
- Bystander's whole raw wire stream asserted to be EXACTLY the five broadcast cues in raise
  order — nothing extra, nothing missing, nothing secret.

### 1b. `ArmBladeExtend_WithRealPvsCulling_ClientOutsidePvsRangeReceivesZeroCuesOnTheWire`

Spec §7's "Integration — PVS scoping" row (grk #3: "`Filter.Pvs` actually applied, not
assumed"). The critical grounding discovery (see §3.5): **the pooled test harness runs with
`net.pvs = false`** (Robust.UnitTesting `PoolManager.DefaultCvars`), and
`Filter.AddPlayersByPvs` short-circuits to *all players* when that CVar is false
(`RobustToolbox/Robust.Shared/Player/Filter.cs` line 71-73) — so W4's confidentiality test, and
any test in the default pool, exercises actor-exclusion/scrubbing but **cannot falsify the PVS
boundary itself**. This test therefore enables the engine's real culling (`net.pvs = true`,
set BEFORE the scenario's entities spawn so the far client never even learns the changeling
exists; restored to the pool default in `finally`), parks the second client's body 500 world
units away (10x beyond `net.pvs_range` 25 x Filter's 2.0 multiplier = 50), fires the
secret-role pair emit (Extend) plus a plain broadcast cue (return-value-asserted), and proves:

- The far client's raw wire stream is **EMPTY** — zero `SolreignFxCueV1` events of any kind:
  not the generic, not the detail, nothing. Transport-level non-delivery, not an honest client
  declining to render.
- Positive controls, so the zero can't be vacuous: the actor still received the real detail
  cue (session-targeted delivery is filter-independent) AND the plain broadcast cue (the
  broadcast fan-out genuinely ran); actor exclusion still holds under real culling.

## 3. Deviations and grounding corrections (the W1-W4 pattern, continued)

1. **File location.** Spec §8 W5's boundary names
   `Content.IntegrationTests/Tests/_Solreign/FxCueTwoClientConfidentialityTest.cs`; the file
   lives one directory deeper, in `Tests/_Solreign/FX/`, beside W4's
   `FxArmBladeConfidentialityIntegrationTest.cs` and W3's
   `SolreignFxEffectsPrototypeConsistencyTest.cs` — the FX test subfolder is the established
   convention this spec's own waves created after the spec was written. Class name kept exactly
   as spec'd.
2. **"Spawns Client A as a changeling entity" (§5.3.1).** Done as `MobLing` +
   `EnsureComponent<SolreignChangelingComponent>` — same as W4's test, same W4-§3 grounding:
   real in-round changelings are component grants onto arbitrary bodies, and the FX cue is
   raised identically regardless of body; the real-antag-granted-body coverage lives in
   `SolreignChangelingTransformCycleIntegrationTest` (W4).
3. **"Built directly on `PlayerDelightTwoClientWireIntegrationTest.cs`" (§5.3).** That class's
   second-client helpers are private to it (its own documented choice); the minimal
   lifecycle subset is reproduced here, exactly as W4's test already did with the same
   rationale.
4. **"Exactly one render activation" (§5.3.6) measured as exactly one ACCEPTED cue per emit.**
   `AcceptedCuesForTests` is recorded at the single point in `SolreignFxCueSystem.OnCueReceived`
   that feeds the `transformation` render hook (`OnTransformationCue`) 1:1 — for the
   Transformation category there is no lease/pool state to count and no per-activation hook on
   the render partial itself. One accepted cue == one render-hook invocation by construction of
   the shipped pipeline; adding a render-side counter would have meant editing W2/W3 files
   outside W5's file boundary for no additional discrimination.
5. **The PVS test had to flip an engine CVar the spec never mentions.** §7 says "same
   two-client fixture, third scenario" — but in the default pool `Filter.Pvs` degenerates to
   all-players (grounded: `PoolManager.DefaultCvars` sets `net.pvs=false`;
   `Filter.AddPlayersByPvs` checks `CVars.NetPVS` first and returns `AddAllPlayers()`). Written
   as spec'd, the test would pass vacuously and prove nothing — the exact "asserted, not
   specified" failure grk #3 flagged. The test enables `net.pvs = true` for its own scope
   (engine supports live toggling: `PvsSystem.SetPvs`), restores it in `finally`, and the pool
   is `Dirty` anyway. This is judged a faithful implementation of the spec's *intent* ("a
   client outside PVS range receives ZERO cues... `Filter.Pvs` actually applied, not assumed")
   over its letter.
6. **Noted, no action — benign broadcast-counter gap on egress drop.** `TryCreate` mints the
   broadcast CorrelationId BEFORE the egress-budget check in `RaiseCue` (the grk H-A ordering
   fix in W2 moved budget AFTER construction), so an egress-dropped broadcast cue burns a
   broadcast id and leaves a gap. This is not a confidentiality side channel — the dropped cue
   is itself a broadcast (non-secret) cue, so the gap correlates with load-shedding, never with
   secret-role activity, and the §5.3.5 property ("detail minting leaves no hole") is exactly
   what the test proves. Recorded so a future reader of a gap in production diagnostics doesn't
   misread it as the grk #6 leak.
