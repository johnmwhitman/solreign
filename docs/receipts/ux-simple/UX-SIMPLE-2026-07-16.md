## FIX 1 — Wingmate guide eligibility gate

**Problem**: the only path that ever made a player guide-eligible was the moderator-only `wingmateapprove` console
command. Without it, pairing was structurally impossible for two ordinary players, and the Volunteer button stayed
silently greyed out with zero explanation.

**What shipped**:
- New CVar `solreign.wingmates.auto_guide_eligibility` (REPLICATED | SERVER, **default TRUE**) —
  `Content.Shared/CCVar/CCVars.SolreignWingmatesAutoGuideEligibility.cs`.
- `WingmateSystem.IsGuideEligible`: an account is eligible if EITHER a moderator has explicitly approved it, OR
  (when the CVar is on) it meets `MeetsAutoEligibilityCriteria` — alive (`MobStateSystem.IsDead`), not a ghost/observer
  (`GhostComponent`), and at or above `CCVars.SolreignWingmatesMinimumShifts` (an existing, previously-unwired CVar,
  default 10) career "tours" tracked in the Season Ledger. The tenure count is fetched lazily on beacon-open and
  cached per account for the process lifetime (career tours only grow, so staleness only ever under-counts).
- `wingmateapprove`/`wingmaterevoke` (`WingmateCommands.cs`) are **unchanged** at the command layer — they still call
  `ApproveGuide`/`RevokeGuide`. Those methods were extended: `RevokeGuide` now also adds the account to a new
  `_deniedGuides` hard-deny set (a grk code-review finding — see below), so a revoke actually overrides the auto path,
  not just the manual-approval flag; `ApproveGuide` clears a prior deny. Both sets are round-local, matching
  `_approvedGuides`' existing lifetime exactly.
- Every gate that used to check `_approvedGuides.Contains(...)` directly (`Offer`, `SetVolunteering`, seeker
  visibility in `BuildPrivateState`) now calls `IsGuideEligible`.
- `WingmateUiState.VolunteerIneligibleReason` (new, optional trailing field — no existing call site broke): an .ftl
  loc key explaining exactly why volunteering is blocked, or null when it isn't. Computed in
  `WingmateSystem.ComputeVolunteerIneligibleReason`. Client (`WingmateWindow.xaml`/`.xaml.cs`) renders it in a new
  `VolunteerIneligibleLabel`, visible only while opted out and blocked. No silent greyed button anywhere in the flow.

Reasons surfaced (never silent):

| Condition | Loc key |
|---|---|
| Auto-eligibility CVar off, not moderator-approved | `wingmates-guide-ineligible-manual` |
| Auto on, but ghost/observer | `wingmates-guide-ineligible-observer` |
| Auto on, but dead/critical | `wingmates-guide-ineligible-not-alive` |
| Auto on, tenure lookup still loading | `wingmates-guide-ineligible-loading` |
| Auto on, below the shifts floor | `wingmates-guide-ineligible-tenure` |
| Anything else unresolved | `wingmates-guide-ineligible-generic` |

### OWNER DECISION — auto vs moderated posture

Per the standing instruction, default is **TRUE** (auto-eligibility on): a `grk` design-sanity pass (run before and
after implementation) flagged this as the single biggest risk in the whole fix, ranked "critical": *"tenure ≠ trust
... auto-approve + text-only pairing + no proximity is a grooming/social-engineering surface ... especially for
minors."* This is a real, un-mitigated-by-code concern — 10 shifts proves familiarity with the game, not
trustworthiness with a newcomer, and Wingmates has no proximity requirement (matching is server-wide, unchanged by
this fix). The existing charter-consent gate, decline/block, and moderator revoke-as-hard-deny (added this session)
are the mitigations that exist; none of them are an age gate or a report path, and this fix does not add one — that
would be a policy/product decision, not a bug fix, and is out of scope here.

**How to flip the posture**: set `solreign.wingmates.auto_guide_eligibility` to `false` on the live box (or via
`server_config.toml`) to restore the pre-fix moderated posture (an admin must run `wingmateapprove` first) — e.g. for
a low-pop canary with staff online, exactly as the original enable plan intended. `wingmateapprove`/`wingmaterevoke`
work identically either way. Recommend John/staff weigh the grk finding above before leaving auto on for a live,
public, mixed-age server.

### grk findings addressed after the design pass

1. **HIGH — revoke didn't stick under auto-eligibility.** `RevokeGuide` only removed `_approvedGuides`; an
   otherwise-qualifying (alive, non-ghost, tenured) account would simply re-qualify via the auto path on its very
   next check. Fixed with the `_deniedGuides` hard-deny set described above. Verified live via
   `RevokeGuideDeniesAutoEligibilityEvenForAnAliveNonGhostSufficientlyTenuredAccount` (integration).
2. **HIGH — thread-unsafe `HashSet` mutation off the ECS thread.** The tenure-fetch failure path used to call
   `_careerToursLoading.Remove(actor)` from inside the async continuation (which can resume on any thread-pool
   thread), racing with the same `HashSet`'s main-thread `Add`/`Remove` calls. Fixed: the failure path now enqueues a
   null-Tours sentinel onto the existing `ConcurrentQueue`, and `DrainLoadedCareerTours` (main-thread only, called
   from `Update()`) is the ONE place that mutates `_careerToursLoading` — same discipline this file already uses for
   `_pendingPersistentBlocks`/`DrainCompletedBlockWrites`.
3. **Revoke-while-paired** (asked for explicitly): already handled correctly pre-existing —
   `RevokeGuide`/`_state.RemoveUser` hard-ends any active pairing immediately, notifying both sides. Pinned with a
   new test, `RevokeGuideWhilePairedDissolvesTheActivePairImmediately`.
4. **Mid-round CVar/floor changes**: only the raw tours COUNT is cached; the pass/fail comparison against
   `SolreignWingmatesMinimumShifts` is re-read and re-evaluated live on every check, so raising the floor mid-round
   takes effect immediately with no cache-bust needed. Pinned with
   `RaisingTheMinimumShiftsFloorMidRound_ImmediatelyDemotesACachedButNowInsufficientAccount` (integration).
5. **Stale UI vs. live enforcement**: the open-beacon UI snapshot isn't continuously repolled every tick (same as
   every other Wingmates UI field) — a player's alive/ghost state changing while they sit with the window open won't
   refresh the reason label until they act again or reopen the beacon. This is a known, accepted limitation (matches
   how `_approvedGuides` itself was never continuously polled either), NOT a bypass: the actual server-side
   `SetVolunteering`/`Offer` gate re-checks eligibility fresh at the moment of the real action, never trusting a
   stale snapshot. Pinned with `LiveEnforcement_NeverTrustsAStaleClientSnapshot_...`.
6. **Reconnect/mid-round join**: tenure cache and rate limiters are keyed by account (`NetUserId`), not session, so a
   reconnect doesn't lose progress (matches the existing `RequestRateLimitWindowSurvivesReconnectForTheSameAccount`
   idiom).

## FIX 2 — Oracle failure feedback

**Problem**: `SolreignOracleSystem.FireWebhook` silently dropped every failure (non-2xx, unverified signature,
malformed body, timeout/exception) — `return;` with no popup and no server log.

**What shipped**:
- Every failure branch now (a) logs server-side via `SolreignOracleSystem.DescribeOracleFailure` (a pure,
  unit-tested static formatter — always includes the HTTP status code; if the body parses to the daemon's hardened
  error contract, `{"error":"oracle_unavailable","reason":"missing_api_key"|"llm_error","detail":"<ExceptionClassName>"}`
  (a signed 503, per a mid-flight daemon-hardening note folded into this fix), also logs the structured reason/detail
  for operators; an older daemon's raw, contract-less 500 or any unparseable body still gets a status-code-only line,
  never throws) and (b) enqueues exactly one in-fiction popup for the player, drained on the main ECS thread in
  `Update()` — never touching entities/popups from the async `Task.Run` continuation, matching this file's existing
  threading discipline for `_pendingOracleResponses`.
- One failure = one popup, never a retry: `FireWebhook` never retried before this fix and still doesn't.
- Player-facing text is always the same three in-fiction variants regardless of the underlying reason — the parsed
  `reason`/`detail` are logged server-side ONLY, never surfaced to the player (verified structurally: the popup path
  and the log path are separate functions with no shared string).
- Daemon-authored `reason`/`detail`/body fields are length-capped before logging (a grk finding —
  `MaxFailureFieldLength`/`MaxFailureBodyLength`) so a compromised or buggy daemon can't flood the server log.

Locale (`Resources/Locale/en-US/_solreign/oracle.ftl`), PG-13 unsettling-corporate, 3 variants (one picked at random
per popup via `IRobustRandom.Pick`):
- `solreign-oracle-failure-popup-hums` = "PROVIDENCE does not respond. The terminal hums."
- `solreign-oracle-failure-popup-static` = "Your petition dissolves into static. Something on the other end declines
  to listen, for now."
- `solreign-oracle-failure-popup-silence` = "The Directive's line goes quiet. Perhaps try again later — the Company
  assures you this is normal."

## FIX 4 — Award feedback (shared "+N Standing — reason" popup)

New `Content.Server/_Solreign/Notifications/SolreignAwardPopup.cs` (static helper, `Show(popup, origin, recipient,
delta, reasonText, type)`, signed delta renders "+N"/"-N"): wraps the same `SharedPopupSystem.PopupEntity` call
convention already used everywhere in `Content.Server._Solreign`. No dedup mechanism exists or is needed — every call
site fires exactly once per one-shot award/spend event, never on a retried/polled path (the closest existing analog,
`SeasonLedgerStore`'s title-grant "announced" gate, exists specifically because titles are re-evaluated every
`LoadTitle` call; nothing here has an equivalent re-evaluation loop).

**Wired in**:
- `ContractsSystem.CompleteContract` (raid-teammate payout ping) and `ContractsSystem.Dropbox.cs` (the depositor's
  own completion popup) — both already had a working, bespoke "+N Standing" string; now routed through the shared
  helper for consistent wording (`solreign-contracts-award-reason-{complete,raid}`).
- `SolreignMarketSystem` (purchase confirmation) — this was the real gap: a successful buy already popped up the item
  name, but never confirmed how much Standing it cost (the daemon's buy ack has no price field). Added a
  `_lastKnownPriceByListingId` cache, refreshed on every inventory fetch/broadcast; a successful buy now shows
  "-N Standing — Bought {item}" when a price is known, falling back to the old item-only popup when it isn't (a
  fresh process that never fetched this console's inventory). **grk finding, addressed**: the price is now
  snapshotted synchronously in `OnBuyMessage` at the moment of the click (not re-queried from the — possibly
  since-repriced — cache at drain time), collapsing the staleness window to "since this exact click" rather than
  "since this console's last inventory fetch."

**Not wired in, and why** (honest scoping — no daemon changes were made, this is a game-only worktree):
- **Bounty claims**: the daemon's claim-verdict wire contract (`ClaimAckDto`) carries only a free-text `msg`, no
  numeric Standing amount. The existing `solreign-bounties-verdict-popup` already surfaces the judged outcome to the
  player (not silent) — fabricating a "+N Standing" number without a real amount from the daemon would be dishonest.
  Wiring a real amount through requires a daemon-side wire-contract change.
- **Salary**: `SolreignRoundOrchestrationSystem`'s round-end POST is fire-and-forget with no response processed at
  all, and the outbound payload doesn't even carry a per-player amount (the daemon computes salary from career rank
  after receiving the roster). There is no local award/amount to hook a popup onto without a daemon-side echo. Flagged
  as a real, known follow-up (matches the diagnostic report's own dead-simple-ify item), out of scope for this
  worktree.
