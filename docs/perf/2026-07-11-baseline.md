# Solreign perf baseline — 2026-07-11

Honest tick-cost data for refinement planning (the `/health` lane). Numbers below are real,
captured from one run of the harness added in this pass — nothing here is estimated or
extrapolated.

## 1. What RobustToolbox already gives us

- **Prometheus metrics ship in the server.** `RobustToolbox/Robust.Server/DataMetrics/MetricsManager.cs`
  exposes an OpenTelemetry/Prometheus-format `/metrics` HTTP endpoint (`CVars.MetricsEnabled` +
  `MetricsHost`/`MetricsPort`), backed by `Prometheus.Metrics.DefaultRegistry`.
- **Per-`EntitySystem` timing already exists, engine-side, at zero extra instrumentation cost.**
  `RobustToolbox/Robust.Shared/GameObjects/EntitySystemManager.cs` wraps every system's `Update()`
  call in a `Stopwatch` (only when `EntitySystemManager.MetricsEnabled == true`) and observes it into
  a Prometheus histogram, `robust_entity_systems_update_usage`, labelled `system="<TypeName>"`. This
  is a `Histogram.Child.Observe()` per system per tick — the same mechanism `TickUpdate` uses to
  gate exception-tolerant execution, so it costs nothing when metrics are off and is genuinely
  server-thread-measured (not wall-clock-through-a-test-harness) when on.
- **`Robust.Shared.Profiling.ProfManager`** is a separate ring-buffer profiler (Tracy/live-profile-
  viewer target) for ad-hoc interactive sampling. It's the right tool for a human staring at a live
  server with the in-game profiler overlay, but its buffer format isn't a convenient thing to
  snapshot-and-diff from an automated test, so the harness below uses the Prometheus histogram
  instead — same underlying instrumentation, easier to read back programmatically.
- **`IGameTiming`/`GameTick`** give tick rate and current sim time; not used directly for cost
  measurement here (the histogram already gives per-tick cost), just for scheduling entities'
  `NextFireTime`-style fields.

## 2. The harness

`Content.IntegrationTests/Tests/_Solreign/SolreignPerfBaselineTest.cs` (test `Baseline`):

1. Starts a real client+server pair and round-starts it on **SolreignOasis** (`PoolSettings.Map`,
   `DummyTicker = false` — the same mechanism `RestartRoundTest`/`MappingTests` already use; this
   is a genuine `GameTicker.RestartRound()` on the actual station prototype, not a bare grid load).
2. Warms up 60 ticks so station post-init (contracts board fill-in via `StationPostInitEvent`,
   atmos seeding, etc.) settles.
3. Spawns a synthetic population standing in for "15 dummy players' worth of mobs" plus a
   representative instance of every Solreign system that carries a per-tick `Update` loop:
   15× `MobHuman`, 8× `SolreignMobUnicorn` (periodic-effect FX), 9× tameable pets, 5×
   `SolreignMobComplianceRetrievalUnit`, 6× `SolreignDormantEnt`, 4× armed `SolreignHotPotatoBomb`
   (detonation pushed an hour out so nothing actually goes off mid-run), 3× RC car + controller
   pairs (left unbound — see caveat below), 5× `SolreignVampireComponent` and 5×
   `SolreignWerewolfComponent` layered onto dummy mobs, and Sprint held down (`C` key) on all 15
   dummies via `SolreignSprintSystem.SetSprintKeyHeld`.
4. Warms up another 30 ticks so `MapInitEvent` fires on everything just spawned (schedules
   `PeriodicEffect`/`DormantEnt` next-fire times, etc.).
5. Flips `EntitySystemManager.MetricsEnabled = true`, snapshots the Prometheus histogram, runs
   **240** ticks one at a time (timing each `WaitRunTicks(1)` call on the wall clock too),
   snapshots the histogram again, diffs before/after per system.

**Analyzer-law compliance note:** every spawn either uses an existing prototype as-is, or adds a
component via `EnsureComponent<T>()` and leaves its fields at their compiled-in defaults. The test
never assigns a field on an `[Access]`-locked component from outside its owning system (would be a
compile-time `AccessAnalyzer` error) — where a system's own API is the only legitimate way to
drive state (Sprint), the test calls that API instead of poking the component directly.

**Known limitation, stated honestly:** RC controllers were spawned idle/unbound (binding is only
reachable through a private `AfterInteract` handler on `RcControllerSystem`), so this pass does not
exercise the "actively driving" branch of `RcControllerSystem.Update`. Given that loop is already
gated by `NextCheck` and the real population of simultaneously-driven RC cars is inherently tiny,
this is a low-priority gap, not a blind spot on anything suspected of being expensive.

## 3. Results (one real run, 240 measured ticks)

### 3.1 Headline number

```
TOTAL entity-system time across all systems: 1169.357ms over 240 simulated ticks
                                           => 4.8723 ms/tick
```

This is the sum of every system's own server-thread `Stopwatch`-measured time, divided by the
actual number of ticks we drove (240 — confirmed against the histogram's own per-system tick counts,
which mostly read exactly 240; see the methodology note below). This is the trustworthy, honest
per-tick entity-system compute cost **under this synthetic stress load**, on this dev machine, in
the multi-threaded IntegrationTest harness (so it does *not* reflect a stripped dedicated-server
build's raw perf, but it is internally consistent and safe to compare against future re-runs of
this same harness).

### 3.2 Wall-clock cross-check (directional only — has harness overhead baked in)

```
min=3.823ms  p50=4.851ms  p95=7.537ms  max=12.303ms  mean=5.190ms   (per WaitRunTicks(1) call)
```

This tracks the histogram-derived 4.87ms figure closely (as it should — entity-system update is
the dominant cost inside a tick), which is a good sanity check that the harness itself isn't lying.
Do **not** read this as a real dedicated server's frame time: `WaitRunTicks(1)` round-trips a
message across a channel to a different thread and waits for idle, so every sample includes
test-harness synchronization overhead on top of the actual tick.

**`PhysicsSystem` alone is ~56% of the entire per-tick entity-system budget.** This is expected and

**The single costliest Solreign-authored system is `SolreignSprintSystem`, and it's #10 out of 335
systems overall** — the only Solreign system that shows up anywhere near the top of the whole-engine
ranking. This is expected, not alarming: Sprint is the one Solreign per-tick loop that is
*legitimately* continuous (it does real stamina-drain arithmetic for every actively-sprinting
player, every tick, by design — see §4) rather than a scheduled/gated check. At 15 players it costs
7.3ms over 240 ticks (≈0.03ms/tick); because it's population-bound with no gating, it is the one
Solreign system whose cost scales roughly linearly with concurrent player count and is worth
re-baselining if the server ever approaches a much larger population than 15.

## 4. Top suspected hotspots — verdict per the task's named suspects, plus what the grep found

A full `override void Update(float` sweep of `Content.Server/_Solreign`, `Content.Client/_Solreign`,
`Content.Shared/_Solreign` found **12 systems** with a per-tick loop (11 server, 1 shared;
everything else — Contracts, Changeling, Corporate, MiniBoss rules, Season1 rules, **Zones/gates**
— is entirely event/`DoAfter`-driven and has zero per-tick cost by construction, confirmed by the
histogram: none of those show up above because they were never sampled as `Update`-based rows in
the first place, they simply have no `Update` method to instrument).

1. **`SolreignPeriodicEffectSystem` (the "unicorn FX" system named in the task)** — already optimal.
   Per-entity `NextFireTime` gate (`Content.Server/_Solreign/Effects/SolreignPeriodicEffectSystem.cs`):
   an `EntityQueryEnumerator` plus a single `TimeSpan` comparison per entity per tick, real work only
   on the tick the effect actually fires. This is the reference pattern the task pointed at, and it
   already exists — nothing to change.
2. **`SolreignHotPotatoSystem` ("HotPotato beeps")** — already well-gated. Per-entity `if
   (!potato.Armed) continue;` plus a `NextBeep` time check; real per-tick population of armed
   potatoes is normally 0-1. No change needed.
3. **"Zone gates" (`SolreignZoneGateSystem`)** — **has no `Update()` loop at all.** It's a pure
   collision/`StepTriggerEvent`-driven teleport system. Zero steady-state tick cost by construction
   — the task's suspicion doesn't apply here.
4. **`SolreignTameableSystem` — the one real, no-excuse cheap win, applied in this pass.** Before
   this change it ran an *unconditional* `EntityQueryEnumerator<SolreignTameableComponent>` every
   single tick with no time gate at all (the only Solreign per-tick loop with that property).
   Live population is small right now (3 pet prototypes on the map, zoo-wing fauna not yet grafted
   per `docs/specs/2026-07-11-map-graft-plan.md`), so this wasn't costing anything today, but it
   had no ceiling once the zoo wing lands. Fixed by adding the same low-frequency accumulator
   `SolreignNightVisionSystem` already uses for its power-cell sync (`_nextOwnerSweep` gate, 2s
   interval) — `Content.Server/_Solreign/Pets/SolreignTameableSystem.cs`. Zero behavior change
   (owner cleanup is not time-critical), verified still compiles and passes in this same benchmark
   run (`SolreignTameableSystem` row above, 0.36µs mean / 0.086ms total — cheapest system on the
   whole Solreign list post-fix).
5. **Other systems surveyed, no change needed:**
   - `SolreignVampireSystem` / `SolreignWerewolfSystem` — per-entity time/state gates already in
     place; `SolreignWerewolfSystem` deliberately uses `AllEntityQuery` instead of
     `EntityQueryEnumerator` for the transform-state loop (documented in the source: `PolymorphSystem`
     parks the wolf body on a paused map, which `EntityQueryEnumerator` would silently skip) — correct
     as written, not a performance bug.
   - `SolreignNightVisionSystem` — the *best* pattern in the pack: a single system-level interval
     gate (`_nextSync`) that skips the entire query, not just per-entity work, most ticks.
   - `SolreignDormantEntSystem` / `RcControllerSystem` — per-entity `NextCheckTime`/`NextCheck` gates,
     already optimal.
   - `ComplianceRetrievalUnitSystem` (Terminator) — mostly gated via `NextPoll`/`StaggeredUntil`;
     the one branch that recomputes an alive/faction check every tick while a target is actively
     locked has no time gate, but touching that risks a visible aggro/deaggro lag for a
     correctness-sensitive antag mechanic with an inherently tiny population (mini-bosses). Flagged
     as a possible future cheap win, deliberately **not** applied this pass — not "risk-free" in the
     same way Tameable's was.
   - `NinjitsuSystem` — per-entity expiry check, tiny live population, fine as-is.
   - `SolreignSprintSystem` (Shared) — **not a candidate for next-fire scheduling.** It is
     legitimately continuous: sprint speed must respond every tick while the key is held, and the
     stamina drain itself is already coalesced into once-a-second lumps
     (`SprintComponent.NextDrainTime`), which is the correct granularity for a continuous input-driven
     mechanic. This is why it's costlier than the others (§3.3) — it is intentionally doing more
     real work per tick, on a bounded (player-count) population, not an unbounded one.

## 5. How to re-run this

```
dotnet test Content.IntegrationTests/Content.IntegrationTests.csproj \
  --filter "FullyQualifiedName~SolreignPerfBaselineTest" -c Debug \
  --logger "console;verbosity=detailed"
```

Run it in isolation (that filter) so the Prometheus histogram diff isn't contaminated by any other
integration test's system activity sharing the same process-wide registry. `pgrep dotnet`/`pgrep
MSBuild` first per house rule — this is the one lane allowed to invoke `dotnet test` for its own
benchmark.
